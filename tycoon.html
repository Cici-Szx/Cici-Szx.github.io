02 / DEFINE THE EXPERIENCE

Campus life.
One decision at a time.

The brief became a simplified Monopoly-style game: recognisable campus places, shared resources and unexpected events. The design priority was a clear, testable scope with visible consequences for each action.

2–4Players sharing one browser
25Spaces around campus
40Chance + Fate cards
1Held card per player
DESIGN QUESTION

How might a familiar board game become a clear, testable campus experience?

01 / CLARITY

Show the next action.

Make a turn explicit. Roll, resolve the space, make a card decision, then move on.

02 / FEEDBACK

Make change visible.

Player colours, cash, ownership and an event log show the effects of each decision.

03 / RELIABILITY

Test the rules directly.

Keep rules independent of the interface so edge cases can be checked without the browser.

03 / CONNECT THE RULES TO THE INTERFACE

Clear outside.
Structured underneath.

A click changes the game state, then the interface redraws from that state. Separating the two keeps the rules inspectable and avoids making the display the source of truth.

→→
ACTION GATING

A decision, at the right moment.

The interface shows actions for the current phase: buy or skip a property, then draw and use, keep or replace a card. A held-card window comes before End Turn.

OWNERSHIP

Colour connects the dots.

Owned spaces use the owner’s colour, connecting the board with player information.

CONSEQUENCES

Every change has a trail.

Cash, position and a recent event log make rule outcomes visible as the game progresses.

CARD TIMING

Make the exceptions explicit.

Card effects can cause movement or an extra roll. Separate phases manage these branches and the one-card hand limit.

NEXT / PLAY-TEST WITH PEOPLE

Correct rules are only the beginning.

The tests establish rule behaviour, not usability or game balance. Next, observe first-time players, check whether card timing is understood, and evaluate pacing, fairness and recovery from mistakes.
